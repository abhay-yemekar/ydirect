# Public repository launch checklist

This checklist optimizes the yDirect showcase for discovery and credibility. It cannot guarantee stars or virality; sustained reach depends on product usefulness, a clear story, authentic distribution, responsive maintenance, and time.

## Repository setup

- [ ] Repository name is `ydirect` under `abhay-yemekar`.
- [ ] Visibility is Public.
- [ ] Default branch is `main`.
- [ ] Description: `Save once. Reuse in seconds — a smart Chrome snippet manager for organized, searchable, portable reusable text.`
- [ ] Website points to the live yDirect product or support page until a dedicated landing page is ready.
- [ ] Social preview uses `assets/brand/social-preview.png`.
- [ ] Issues are enabled.
- [ ] Discussions are enabled after there is capacity to moderate them.
- [ ] The repository is pinned on the owner's GitHub profile.

## README launch gate

- [ ] Hero renders correctly at desktop and mobile widths.
- [ ] GIF starts quickly and remains readable.
- [ ] Static screenshot is available below the GIF for accessibility and detail.
- [ ] Store status and install instructions are current.
- [ ] No unverified users, stars, ratings, speed, or time-saved claims appear.
- [ ] Owner and support contacts work.
- [ ] Privacy, terms, support, license, and security links work.
- [ ] The private-source boundary is visible near the top and in the license section.

## Launch sequence

### Day 0 — repository

1. Publish the repository with the initial product-story commit.
2. Set description, website, topics, social preview, and Discussions.
3. Create a `v1.3.1-showcase` GitHub release only after the product/store status in the notes is accurate.
4. Pin the repository on the GitHub profile.

### Store launch day

1. Complete the owner-controlled final Chrome Web Store check.
2. Publish the approved extension.
3. Replace every “review pending” note with the verified store link.
4. Test install from a clean Chrome profile.
5. Publish the LinkedIn launch post with the native product-tour video and repository link.

### First week

1. Share a problem-first product story, not only a feature list.
2. Ask a small number of relevant peers for specific feedback—not automatic stars.
3. Respond to every useful issue or discussion promptly and transparently.
4. Turn repeated questions into FAQ improvements.
5. Share one technical decision (permission minimization), one Product Owner decision (scope/roles), and one user workflow on separate days.

## Ethical reach principles

- Do not buy stars, trade stars, run giveaways tied to stars, or automate GitHub engagement.
- Do not mass-post unrelated communities.
- Do not claim “open source” when the source is private.
- Do not create fake testimonials, download counts, benchmarks, ratings, or users.
- Prefer a useful demo, honest trade-offs, and responsive maintenance.

## Content angles

- **Problem story:** why repeated text becomes hidden productivity debt.
- **Product decision:** why yDirect copies instead of automatically reading or inserting page content.
- **Privacy decision:** how user-triggered `activeTab` access avoids persistent all-site injection.
- **Architecture story:** local-first work with optional cloud recovery and scoped collaboration.
- **Product Owner story:** defining roles, non-goals, release gates, and truthful product claims.
- **Build-in-public story:** public accountability without publishing proprietary source.

## After measurable usage exists

Add verified metrics only with dates and definitions, for example:

- published Chrome Web Store users and rating;
- median time from opening yDirect to copying a snippet;
- successful first-run completion;
- backup restore test completion;
- issue response and resolution trends.

Never backfill estimates as observed results.
